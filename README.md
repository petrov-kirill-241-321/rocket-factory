# Rocket Factory

Микросервисная система обработки заказов на сборку технического изделия.
Учебный проект на Go, написанный для того, чтобы показать не набор технологий,
а решение конкретных задач распределённой системы: как не потерять событие,
как не списать деньги дважды, как не «подвесить» заказ навсегда и как потом
найти концы в логах.

**Стек:** Go 1.25, HTTP (`net/http`), gRPC, Kafka, PostgreSQL, Redis, Nginx,
Docker Compose, Prometheus, Grafana, OpenTelemetry, Jaeger.

---

## Что делает система

Пользователь оформляет заказ на сборку изделия — например, двигатель и два
топливных бака. Дальше заказ проходит через четыре независимых сервиса:

```
резервируем комплектующие → берём оплату → запускаем производство → отгружаем
```

Каждый шаг может завершиться отказом, каждый сервис может упасть в любой момент,
и система обязана из этого выйти в понятное состояние: либо заказ завершён,
либо помечен как неуспешный, а удержанные комплектующие возвращены на склад.

Именно эти «неудобные» ситуации — основное содержание проекта.

### Жизненный цикл заказа

```
created ──▶ inventory_reserved ──▶ paid ──▶ production_started ──▶ completed
   │                 │                │              │
   └──▶ inventory_failed              └──────────────┴──▶ failed
```

## Сервисы

| Сервис | Отвечает за | Публичный HTTP |
| --- | --- | --- |
| `auth-service` | пользователи, вход, выдача JWT | да |
| `order-service` | каталог, заказы, их статусы | да |
| `payment-service` | оплата (симуляция провайдера) | да |
| `inventory-service` | остатки и резервы комплектующих | нет |
| `production-service` | производственные задачи | нет |

Наружу через Nginx выведены только три сервиса. `inventory-service` и
`production-service` живут внутри сети и работают исключительно на событиях.

Подробный разбор каждого — [docs/services.md](docs/services.md).

## Запуск

Нужны только Docker и Docker Compose. Go локально не требуется — сборка идёт
внутри образа.

```bash
git clone <repo> && cd rocket-factory
cp .env.example .env
docker compose up --build
```

API поднимется на `http://localhost:8080` (порт задаётся `NGINX_PORT` в `.env`).

Со стеком наблюдаемости:

```bash
make up-observability
```

Полная инструкция, включая очистку данных и работу с миграциями, —
[docs/local-run.md](docs/local-run.md).

## Проверка основного сценария

Автоматически:

```bash
./scripts/smoke.sh
```

Скрипт проходит весь путь заказа и проверяет результат на каждом шаге, включая
отказ при повторной оплате и формат ошибки при отсутствии токена.

Вручную:

```bash
BASE=http://localhost:8080

# 1. Регистрация — сразу возвращает токен
TOKEN=$(curl -s $BASE/api/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"pilot@example.com","password":"password123"}' | jq -r .token)

# 2. Создание заказа. Цену клиент не передаёт — её определяет каталог
ORDER_ID=$(curl -s $BASE/api/orders \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: demo-1" \
  -d '{"items":[{"sku":"ENGINE-X1","quantity":1},{"sku":"FUEL-TANK","quantity":2}]}' \
  | jq -r .id)

# 3. Через пару секунд склад должен подтвердить резерв
sleep 3
curl -s "$BASE/api/orders/$ORDER_ID" -H "Authorization: Bearer $TOKEN" | jq .status
# inventory_reserved

# 4. Оплата
curl -s "$BASE/api/orders/$ORDER_ID/pay" \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: demo-pay-1" -d '{"simulate":"success"}' | jq

# 5. Через ~10 секунд производство завершается
sleep 10
curl -s "$BASE/api/orders/$ORDER_ID" -H "Authorization: Bearer $TOKEN" | jq .status
# completed
```

Все эндпоинты с примерами — [docs/api.md](docs/api.md).

## Метрики, логи, трассировки

| Что | Где | Комментарий |
| --- | --- | --- |
| Логи | `docker compose logs -f <service>` | JSON, с `request_id` и `trace_id` |
| Метрики | http://localhost:9090 | Prometheus, профиль `observability` |
| Дашборд | http://localhost:3000 | Grafana, admin/admin |
| Трассировки | http://localhost:16686 | Jaeger, профиль `observability` |

Prometheus, Grafana и Jaeger поднимаются только с профилем `observability`
(`make up-observability`), чтобы обычный запуск был легче.

**Kibana и стек ELK в проекте не используются.** Логи пишутся в stdout в формате
JSON и читаются через `docker compose logs`. Централизованного сбора логов нет —
это осознанное ограничение учебного проекта.

Как по одному `order_id` пройти путь заказа через все сервисы —
[docs/observability.md](docs/observability.md).

## Инженерные практики в проекте

Ниже — то, что действительно есть в коде, а не список технологий из вакансии.

**Transactional outbox.** Событие пишется в таблицу `outbox_events` в одной
транзакции с изменением состояния, а публикуется отдельным фоновым процессом.
Падение сервиса между коммитом в базу и отправкой в брокер не теряет событие.

**Идемпотентность на трёх уровнях.** Заголовок `Idempotency-Key` в Redis как
быстрый фильтр, уникальные индексы в PostgreSQL как источник истины, таблица
`processed_events` для событий Kafka. Отказ Redis не блокирует запись.

**Устойчивость к повторной и неупорядоченной доставке.** Kafka гарантирует
доставку «хотя бы один раз», а порядок между разными топиками не гарантирует
вообще. Статусы заказа упорядочены по рангу, применяется только более позднее
состояние — поэтому заказ не может застрять из-за перестановки событий.

**Повторы и DLQ.** Консьюмер коммитит смещение только после успешной обработки.
Временные ошибки повторяются с нарастающей паузой, неисправимые сразу уходят
в `rocket.dlq`.

**Работа с деньгами.** Суммы хранятся как `int64` в копейках. `float64` для
денег не используется нигде.

**Сквозная трассировка.** `traceparent` передаётся через HTTP-заголовки,
метаданные gRPC и заголовки Kafka. Для outbox контекст сохраняется в колонке
`trace_context`, потому что публикация происходит позже и в другой горутине.

**Явные блокировки и защита от гонок.** `SELECT ... FOR UPDATE` при изменении
остатков и статусов, сортировка позиций по SKU для предотвращения взаимных
блокировок, частичные уникальные индексы против двойной оплаты.

**Graceful shutdown.** Сервис перестаёт принимать запросы, дожидается фоновых
задач и только потом закрывает соединения с БД, Redis и Kafka.

**Слоистая архитектура.** `domain` → `usecase` → `repository` → `transport`.
Бизнес-логика не знает про HTTP, gRPC и Kafka.
